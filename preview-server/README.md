# Preview server

The existing preview hostname serves a compiled Astro Node SSR process behind Caddy and the existing Strapi administrator forward-auth service. The public Gatsby build is unchanged. Per the revised WEB-40 direction, this replaces the preview service directly rather than running a separate candidate alongside Gatsby. This configuration has not itself been deployed or validated on the host.

The workflow builds and publishes commit-SHA image tags and deploys their immutable registry digests without CMS credentials. The SSR build omits the CMS-backed sitemap and does not fetch content; `STRAPI_TOKEN` and `GATSBY_STRAPI_API_URL` are provided at runtime. `ASTRO_CONTENT_MODE=draft` is enforced by Compose. `PUBLIC_RUNTIME_API_BASE_URL`, `PUBLIC_MAPBOX_API_KEY`, `GATSBY_STRAPI_API_URL` and optional `STRAPI_MEDIA_ORIGINS` are image build arguments: browser settings and allowed image origins are compiled into the bundle, so rebuild when these change. Use the workflow variables `PREVIEW_PUBLIC_RUNTIME_API_BASE_URL`, `PREVIEW_PUBLIC_MAPBOX_API_KEY`, `GATSBY_STRAPI_API_URL`, and `STRAPI_MEDIA_ORIGINS`; public keys must not be secrets. The runtime token is separate from the administrator login cookie.

Before rollout, verify the preview hostname's Cloudflare rule **bypasses caching for every path**, its certificate, CMS iframe origin, and administrator authentication. Caddy sets `private, no-store`, `noindex, nofollow`, and a frame-ancestors policy on all responses; the explicit edge bypass is still required. Review the Caddy frame-ancestors list against the actual editor origin. Configure `PREVIEW_FRAME_ORIGINS` for Astro's direct internal responses. Cross-site iframe cookies may be blocked by browsers; signing in through a direct preview tab is a fallback.

On first setup copy `example.env` to `.env`, set the runtime values, and restrict its permissions. Create `caddy-config` next to the Compose file and copy `Caddyfile` into `caddy-config/Caddyfile`. The directory mount allows updates to be seen on reload. The first deployment of this updated mount recreates Caddy; schedule and verify that change. The workflow starts only the listed services without forcing recreation of the whole stack and retains old images. A rollback requires restoring the prior image **and matching Compose/Caddy configuration**; an old Gatsby image alone is not compatible with the Astro proxy port and refresh configuration. Retain those artifacts and arrange rollback before deployment. The previous plan's parallel Gatsby preview and proxy-switch rollback no longer apply.

Caddy proxies `/login`, `/logout` and `/auth/*` to the existing auth service. All other paths, including assets, `/_health/live`, `/_health/ready` and `/__refresh`, pass administrator verification first. There is no Gatsby refresh webhook bypass; remove the obsolete refresh webhook registration separately after rollout, without touching public publish-triggered builds. Login uses Strapi `/admin/login`, then verifies the HttpOnly, Secure, SameSite=None cookie via `/admin/users/me`. Administrator credentials are required. Login redirects preserve relative deep links. Auth requests have a five-second timeout, fail closed on errors, and do not log credentials or upstream response bodies. Caddy access logging is disabled to avoid recording draft URLs.

Inside the private network `/_health/live` checks the process, while `/_health/ready` checks a small authenticated draft collection read with a five-second timeout. Readiness returns 503 for configuration, CMS or credential failure; liveness does not prove dependency readiness. Neither is anonymously reachable through Caddy. The Strapi SDK used for normal content reads currently limits the wait for response headers to ten seconds but does not bound a stalled response body. Treat that as an outstanding reliability limitation to verify and resolve before deployment.

After deployment, test anonymous access and headers on all draft-bearing paths and assets, login/expiry/logout, deep links, iframe and third-party cookie behavior. Check new, renamed, deleted, published and incomplete saved drafts without rebuilding; verify Cloudflare cache status. Exercise CMS and auth outages and restore service. Record real-host startup, memory, p50/p95 response times and save-to-reload freshness. These host checks remain outstanding until performed; the local build does not establish them.

For the GitHub deployment workflow, configure `PREVIEW_SERVER_HOST`, `PREVIEW_SERVER_USER`, `PREVIEW_SERVER_SSH_KEY`, and `STRAPI_TOKEN` as secrets. Set `GATSBY_STRAPI_API_URL`, `PREVIEW_DOMAIN`, `PREVIEW_CERTS_PATH`, `PREVIEW_FRAME_ORIGINS`, and the public build variables described above as repository variables. The workflow uses ports 8443/8080 as in the previous deployment; verify the host forwarding and certificate paths before use. It writes the host `.env`; restrict the deployment account and `.env` permissions. Keep the SSH credentials and registry access scoped to the deployment account.
