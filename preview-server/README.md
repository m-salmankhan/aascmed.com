# Protected Astro preview

This review-only configuration replaces the custom Strapi administrator login with Cloudflare Access. Access authenticates editors separately from the CMS; Strapi remains responsible for CMS login. The existing preview hostname routes through Cloudflare Tunnel to a private Caddy proxy and compiled Astro SSR service. No service publishes a host port. Caddy applies `private, no-store`, `noindex, nofollow` and the framing policy to all responses, and removes Access credentials before proxying. Only the tunnel, Caddy and Astro containers should join their private network; anyone with host or container-network access can bypass this boundary.

Cloudflared 2026.10.5 and Caddy 2.11.7 are pinned to multi-platform image digests. Review upstream security releases and update those digests deliberately. The tunnel config enables URL normalization and requires `cloudflared` to validate a Cloudflare Access assertion against the configured team and application audience before proxying every path. Other hostnames match a 404 catch-all. This does not rely on a custom JWT implementation. [Cloudflare origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/) and [locally managed tunnel config](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/configuration-file/) describe the supported settings. Cloudflare recommends remotely managed tunnels for most uses; local management here keeps the reviewed ingress and Access requirement with this deployment.

The workflow builds a preview image for PR review and publishes a digest-addressable image on main or manual invocation. It does **not** deploy. There are no Cloudflare account or host changes in this branch. The SSR build omits the CMS-backed sitemap and does not need the CMS or its token. `GATSBY_STRAPI_API_URL`, `STRAPI_MEDIA_ORIGINS`, `PUBLIC_RUNTIME_API_BASE_URL` and `PUBLIC_MAPBOX_API_KEY` are build-time origins/browser-visible values supplied through workflow variables; rebuild when they change. `STRAPI_TOKEN` and the tunnel credentials are runtime secrets, not build arguments.

## Account preparation after review

1. Confirm the domain is managed by the intended Cloudflare account and use its [Zero Trust free plan](https://www.cloudflare.com/plans/zero-trust-services/) within its 50-user allowance. Check current plan terms and any identity-provider costs before enabling features. No new server is required. Configure a Zero Trust team, noting its account ID and team name.
2. Under **Integrations → Identity providers**, add the desired Google and/or Microsoft Entra provider and enable [one-time PIN](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/) for email login if desired. Multiple providers and OTP can coexist. New Zero Trust organizations default to the Cloudflare identity provider; OTP must be added explicitly. Provider setup may require its own OAuth registration or admin consent.
3. Under **Access controls → Applications**, create a self-hosted Access application covering the exact preview hostname and all paths. Create an **Allow** policy listing the individual editor email addresses, with the desired login methods, session duration, and MFA policy. Avoid an everyone or broad email-domain allow rule. Obtain the application's audience tag. Access does not automatically track Strapi administrators: maintain this allowlist when editors join or leave. Test an allowed and denied identity; consider OTP's dependence on email account security.
4. [Create a locally managed tunnel](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/create-local-tunnel/) using `cloudflared tunnel login` and `cloudflared tunnel create <name>` on an authorized administrative machine. Record the tunnel UUID and copy its generated JSON credentials securely to the deployment account. Keep the account-wide `cert.pem` off the runtime host where possible; the tunnel-specific credentials suffice to run it. Restrict the credentials and `.env` to the deployment user (`chmod 600`). Keep backups of the previous image, Compose, proxy and DNS configuration for an agreed rollback.
5. Create an explicit Cloudflare **cache bypass for every path** on the preview hostname. Verify the edge rule and headers before editors use it; origin no-store is not a substitute for edge configuration. Set `PREVIEW_FRAME_ORIGINS` to the exact HTTPS CMS editor origin, or space-separated exact origins if there is more than one. Both Caddy and Astro use this list; preflight rejects missing values, wildcards, paths and other non-origin values. The Access application, bypass and DNS changes can affect the existing preview immediately, so schedule them with the cutover. Replace the existing preview DNS record with the tunnel's proxied `<UUID>.cfargotunnel.com` record only during the approved rollout; resolve any existing DNS conflict deliberately.

## Host preparation and manual rollout

Place the reviewed Compose/Caddy files and renderer in the existing deployment directory on the deployment account, retaining the same Compose project identity; do not launch a second stack alongside the old public origin. Copy `example.env` to `.env`, fill in the exact image digest, runtime CMS values, hostname, account ID, Access team and AUD, tunnel UUID and **absolute** paths to the tunnel credentials and generated config. The config file must be separate from the credential file. Prepare `caddy-config/Caddyfile` from the reviewed Caddyfile. Node.js is required on the host for the preflight renderer. Run the following only after the reviewed account setup and rollout are authorized:

```sh
chmod 600 .env
set -a
. ./.env
set +a
chmod 600 "$TUNNEL_CREDENTIALS_FILE"
node render-tunnel-config.mjs
mkdir -p caddy-config
cp Caddyfile caddy-config/Caddyfile
podman compose config --quiet
podman compose run --rm --no-deps cloudflared --config /etc/cloudflared/config.json tunnel ingress validate
podman compose up -d preview caddy cloudflared
```

Preflight checks the credential file's mode, shape and matching account and tunnel IDs and refuses missing/invalid settings. It writes the config atomically as mode 600 without copying the secret. Do not proceed after any failure or use a previously generated config after changing the settings; re-render and validate it. The Compose file requires all values and mount paths, but cannot itself check that an old config matches newly supplied variables. `:Z` gives these private mounts appropriate labels on SELinux systems; review host-specific volume and rootless Podman behavior before rollout. Verify the intended preview image reference is the reviewed `@sha256:` digest, not a mutable tag.

Replacing the prior public Caddy service changes its mounts and port bindings; it will be recreated once. Confirm no old Caddy process or other container still publishes 80/443 or can reach the preview network; stop the obsolete `preview-forward-auth` container after confirming it is not shared. Confirm host firewall rules and external probes cannot reach Astro or private Caddy directly. Only then route the public hostname to the tunnel, test and monitor it. Do not remove the public publish-build webhook; the old Gatsby `/__refresh` registration is obsolete and can be removed separately after cutover.

The pinned cloudflared CLI can validate ingress locally but that does not prove the configured Access app, allowed users, DNS, cache or tunnel connection. Test missing, forged, expired and wrong-audience assertions, logged-out and denied identities, every draft/asset path and health route, refresh, logout, DNS and direct-origin bypasses. Test save, rename, delete and incomplete drafts without rebuilding, plus CMS and Access outages. Record real-host startup, memory, p50/p95 and save-to-reload freshness. The Strapi SDK used by normal content reads currently times out waiting for headers but does **not** bound a stalled response body; resolve that reliability gap before rollout. The pinned Astro standalone adapter has no SIGTERM drain handler. Compose runs an init process so SIGTERM reaches Node instead of hanging at PID 1; this terminates promptly but does not guarantee that in-flight requests drain. Verify shutdown behavior on the host.

## Embedding and recovery

Cross-site iframe authentication depends on browser cookie policy and whether Cloudflare Access and the chosen IdP permit their login flows to appear in a frame. Configure the Access cookie appropriately for the real CMS origin and test Chrome, Safari and the actual editors' browsers, including expiry and reauthentication. Third-party cookie blocking can still break an iframe; direct preview in a tab is a fallback, not proof of iframe acceptance. See [Access cookie settings](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/).

`/_health/live` checks the process; `/_health/ready` performs a five-second authenticated draft collection read. Both are protected through the tunnel. Check them privately as needed; liveness alone does not establish CMS readiness. For rollback, restore the recorded DNS, image and matching prior Compose/proxy configuration together and verify access controls; an old Gatsby image is not compatible with the new Astro port or Access topology. Keep old artifacts until recovery has been exercised.
