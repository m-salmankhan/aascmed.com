## Ownership and repository boundaries

| Repository | Responsibility |
| --- | --- |
| Website | Own Astro source and tests. After a merge to `main`, CI builds the compiled Node SSR preview image, publishes it privately to GHCR and automatically requests deployment in the preview repository. Image builds do not use draft data or runtime secrets. The existing public static site remains a separate deployment. |
| `git@github.com:Allergy-Asthma-and-Sinus-Centers/preview.aascmed.com.git` | Own the preview authentication service/image, Ansible inventory/roles/playbooks, Podman Quadlets, Traefik configuration, tests, beginner runbooks and the CI deployment workflow. Successful auth-image builds and platform/configuration changes on `main` automatically deploy through this workflow too. |

No Git submodules, deployment wrapper image, or VPS builds are planned. The website and auth repositories publish separately versioned images. A release record names exact GHCR **digests** and source commits for both, plus the pinned proxy image and matching configuration revision. Reviewed source and successful CI checks authorize automatic release; selecting each new digest must not require another manual edit, approval or operator command. Never deploy a mutable `latest` tag.

The preview repository's deployment job runs Ansible over SSH with access to protected deployment credentials and runtime secrets. Build/test jobs remain separate and have no VPS credentials or runtime secrets. Pull-request code must never run with deployment credentials. Authenticate cross-repository deployment requests, verify their source repository, successful trusted `main` build, commit and published digest, and load deployment code only from the trusted preview `main` revision. Serialize deployments per host and reject stale/out-of-order requests so a slow older build cannot replace a newer release. Record the complete attempted and successful release sets outside the VPS for repeatable deployment and recovery. WEB-51 must establish the event, release-record and trust contracts before implementation.

Normal operation is **merge → tests/build → private image publication → automatic Ansible configuration/deployment → health checks**. A failed build never deploys. An optional CI rerun/recovery trigger is for retries and rebuilds; it is not the normal release mechanism. Initial actual-host validation and the established hostname's cutover remain the explicit WEB-41/WEB-42 gates; once enabled for that target, routine releases require no separate manual deployment approval.

The future Astro environment contract is `STRAPI_API_URL` for the server-side CMS URL, a separate restricted read-only Content API token for draft reads, and `PUBLIC_RUNTIME_API_BASE_URL` / `PUBLIC_MAPBOX_API_KEY` for intentionally browser-visible build settings. Use runtime secret files for the CMS token and auth signing key; adapt the application to read those files as part of future implementation. The Gatsby retirement MR promotes Astro to the root and removes Gatsby/legacy preview configuration from source. Keep old host credentials and immutable artifacts privately for rollback until acceptance; the root application reads only `STRAPI_API_URL` and the documented `PUBLIC_*` settings. See the [current environment inventory](../docs/environment-variables.md). The CMS URL and browser settings are not credentials; document which values are embedded at build time and require a new image when changed.

## Server and routing

The owner provisions a fresh compatible VPS manually and supplies the CI SSH public key during provisioning. Register its address and independently verified SSH host identity in protected deployment settings before the first run; do not disable host-key verification or trust an unverified `ssh-keyscan`. Terraform is out of scope for now. A replacement server needs the same provider-side provisioning and target/host-identity update, then CI must perform the complete bootstrap and deployment without hand-editing files or running setup commands on the server. The owner does not need Ansible installed on a laptop.

Keep preview-specific services, networks, paths and configuration grouped so Ansible can later target a compatible dedicated Hetzner server. Sharing that host with other websites requires deliberate reverse-proxy/port ownership and per-site networks/state; it is not part of this initial VPS implementation.

Recommend Debian 13 on x86_64, with systemd and a Podman version whose Quadlet features have been verified on the selected VPS image. Ansible installs and configures system-managed Quadlets: systemd manages the containers through rootful Podman operations (Podman has no persistent engine daemon), while Traefik, auth and Astro run as explicit non-root container processes with dropped capabilities, no privilege escalation and read-only filesystems where feasible. Rootful Podman is not rootless isolation; host root and the engine remain privileged. Set appropriate file ownership, port and network permissions, cgroup v2, SELinux/AppArmor policy and persistent writable paths deliberately. Rootless Quadlets are an alternative for later evaluation, not an implied requirement for the first deployment. [Podman Quadlet documentation](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html)

Traefik is the only service publishing host ports 80 and 443. Auth and Astro are reachable only over the private container network; restrict access to that network and the host because other local containers or host administrators could bypass the proxy. Traefik uses an explicit file provider and fixed service/router configuration, with no Podman or Docker engine socket. Do not expose an unauthenticated dashboard. Route login and logout explicitly to auth; apply forward authentication to every other preview route, including static assets and HTTP health endpoints, with failure closed. Only minimal approved identity headers should be forwarded, after stripping browser-supplied equivalents and credentials. Restrict trusted proxy headers to verified upstream addresses; configure rate limiting based on a trustworthy client address. Apply no-store/noindex and an exact configured CMS `frame-ancestors` policy to every response, including static assets, errors and login responses. Configure and verify a Cloudflare cache bypass for the entire preview hostname.

Traefik obtains and renews certificates using ACME DNS-01. Use a Cloudflare API token scoped to the needed zone with Zone Read and DNS Edit, supplied only to Traefik as a mounted secret; persist and protect ACME account/certificate state. Test against the ACME staging service before production and exercise renewal. DNS-01 is certificate verification, not user authentication. [Traefik ACME documentation](https://doc.traefik.io/traefik/v3.4/https/acme/) and [Cloudflare DNS provider permissions](https://go-acme.github.io/lego/dns/cloudflare/).

## Authentication and editor behavior

On login the auth service sends credentials to Strapi's administrator login over HTTPS, validates the returned administrator identity and required active/role status via the appropriate admin endpoint, and immediately discards the upstream administrator token **and any refresh cookies**. Do not forward either to the browser, Astro or logs. Fail closed for network failures, timeouts, invalid responses and unavailable session storage. Strapi may create a temporary upstream session during login, even though preview discards its tokens. Any upstream cleanup must target only that new session and must never revoke the editor's existing CMS browser session. Preview does not retain upstream credentials or use Strapi sessions for subsequent requests.

Issue a separate signed preview JWT in a Secure, HttpOnly cookie using an explicitly fixed allowed algorithm, issuer and audience, expiration and unique `jti`. Initial policy: **eight-hour absolute lifetime and one-hour inactivity timeout**, subject to implementation and editor testing. Maintain an active-session record keyed by `jti` in a small, private, persistent SQLite file; check it on each authenticated request and update idle state safely. Logout revokes the preview session immediately. Handle concurrent requests, expiration, restart, cleanup and signing-key rotation explicitly. A signed JWT alone cannot guarantee immediate logout without server-side state. No separate database server is needed. Preview logout does not log out of Strapi, and CMS logout or role changes do not automatically revoke an already issued preview session; an administrator whose CMS access changes can retain access until preview session expiry or explicit revocation. Document this tradeoff and provide an operator revocation procedure.

Protect login/logout against CSRF and untrusted redirect destinations, validate request size and content, rate-limit failed attempts, use bounded upstream calls, and do not log credentials, tokens, CMS bodies or draft URLs. Keep preview JWT signing material separate from Strapi Content API tokens, registry credentials and DNS tokens. Plan signing-key rotation with an explicit choice between a short verification overlap and signing out all sessions; do not restore a compromised key during rollback.

Saved drafts are fetched at request time, including new and renamed documents; there is no Gatsby refresh endpoint or rebuild for a save. Restore the CMS URL-resolution and verified saved-draft refresh integration only after Gatsby retirement, validating message origin and source. Unsaved editing is not promised. Check newly created, renamed, deleted, published and incomplete drafts and avoid generating malformed preview URLs. Cross-site cookies and identity redirects can prevent iframe login even when headers are configured. Test the actual CMS origin and editor browsers; a direct preview tab is a fallback, not evidence that iframe acceptance passed.

## How Ansible fits

Ansible is the setup checklist executed by a CI runner. Its playbooks describe the desired server state, check the server, and make only the changes needed to reach it; they do not rely on remembering which commands were run last time. An inventory identifies the target VPS, roles group related setup tasks, and handlers restart affected services when configuration changes. Pin the Ansible environment in CI. Use the same automation for first bootstrap and later updates, including a safe transition from the provider's initial SSH user to the deployment user without losing access. Verify repeat runs are safe and understandable. No paid Ansible controller is required.

Use GitHub's encrypted repository secrets directly for the SSH private key and runtime credentials. Keep secrets out of Git, so there is no additional Ansible Vault file or unlock password to manage. This applies the owner's Ponytail/YAGNI instruction while retaining encryption at rest and keeping runtime secrets out of our build/PR jobs. GitHub Free is sufficient; workflow editors remain trusted with deployment access, rather than relying on paid environment branch restrictions. The trusted deployment job creates temporary owner-readable Ansible input files for that run and removes them afterward. Ansible installs scoped, owner-readable secret files on the server; tasks handling them use `no_log`. Plaintext is not echoed into CI output, uploaded as artifacts, cached, or placed in world-readable environment files or images. Restrict each mounted file to its consumer. [GitHub encrypted secrets](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions).

Stage Strapi/Cloudflare credentials with their matching release so a failed update can restore a compatible working set. Never roll the global preview signing key back; rotation invalidates old sessions. Disable credential rollback when replacing a known-compromised token, and fail closed if the replacement cannot be validated. For normal rotations, verify the new dependency (including actual DNS-01 issuance/renewal for the DNS token) before revoking the old value.

The beginner guide must separate the one-time provider/CI setup from automatic operation: creating the VPS, adding the public key, verifying its identity, registering protected settings/secrets, reading CI results, dry-run limits, retries, updates, rotation and recovery. Explain inventory, playbooks, roles, handlers and Vault in plain language. Provide concrete CI actions and expected results; laptop commands may be optional troubleshooting aids, never prerequisites for deployment.

## Delivery and recovery

After WEB-46, populate the supplied preview repository and implement in reviewable increments: authentication and its tests; platform/Quadlet/Traefik provisioning; immutable preview-image packaging; CMS/editor integration; then deployment, acceptance and recovery evidence. The ticket index records the board's actual dependency links. Before any real-host rollout, review the generated configuration, exact image digests, secret boundaries, DNS and rollback procedure. A deployment pre-pulls images, validates Quadlets and Traefik, starts the required private services, checks liveness and dependency readiness, and then checks the protected route. Failure must leave or restore the last known-good compatible image/configuration set. A single-instance replacement may briefly interrupt service; use parallel instances only if a measured uptime requirement warrants their complexity.

Retain previous reviewed image digests, matching service/config versions, persistent session state and recovery instructions for the agreed retention period. Plan for DNS, certificate state and authentication-signing-key compatibility; never reinstate a compromised secret as part of rollback. Do not restore stale session records that could resurrect revoked sessions; disaster recovery should invalidate existing preview sessions and require a fresh login. Verify boot recovery, restore, token rotation, Strapi/auth outages, missing/invalid session behavior, anonymous access, cache headers and real iframe behavior on the new host. Measure startup, memory, latency and saved-draft freshness; local build results do not substitute for host evidence.

Keep encrypted CI secrets, compatible release records and required certificate-state backups outside the disposable host. Recreating the server must not depend on files that existed only on the destroyed VPS. Validate the full replacement exercise from a blank compatible host through CI, including certificate recovery/reissuance and invalidation of old preview sessions. Record the remaining provider/target registration steps honestly; manual VPS provisioning does not provide zero-input infrastructure recreation.
