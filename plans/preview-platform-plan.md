# Deferred preview platform plan

Status: architecture agreed 30 October 2026; **implementation is deferred until Gatsby retirement (WEB-46)**. This is a plan, not a runbook for an existing system: the VPS, preview repository, services, credentials, DNS, and deployment tooling have not been provisioned. Editorial preview may be unavailable during the transition. Public Astro cutover and Gatsby retirement do not depend on the replacement preview being available.

The previous plans for parallel Gatsby/Caddy preview, a direct replacement on the old host, and Cloudflare Access plus Tunnel are superseded. The new platform runs on a new VPS. Cloudflare remains the DNS/CDN provider; Cloudflare Access, Tunnel, and SSO are not part of this implementation. The existing CMS login remains separate; editors use the same Strapi administrator credentials to sign into preview, with a distinct preview session. Shared SSO can be considered later.

## Ownership and repository boundaries

| Repository | Responsibility |
| --- | --- |
| Website | Own Astro source and tests. CI builds the compiled Node SSR preview image and publishes it privately to GHCR; builds do not use draft data or runtime secrets. The existing public static site remains a separate deployment. |
| `git@github.com:Allergy-Asthma-and-Sinus-Centers/preview.aascmed.com.git` | New private repository for the preview authentication service and its image, Ansible inventory/roles/playbooks, Podman Quadlets, Traefik configuration, tests, and beginner-oriented operational documentation. Create and populate it only when the deferred work is authorized. |

No Git submodules, deployment wrapper image, or VPS builds are planned. The website and auth repositories publish separately versioned images; a reviewed deployment configuration names exact GHCR **digests** for both, plus pinned proxy images. CI builds/tests and publishes images without SSH access to the VPS or runtime secrets. Deployment is an explicit Ansible run from an operator's laptop, with controlled private registry access and no unattended promotion.

The environment contract is `STRAPI_API_URL` for the server-side CMS URL, a separate restricted read-only Content API token for draft reads, and `PUBLIC_RUNTIME_API_BASE_URL` / `PUBLIC_MAPBOX_API_KEY` for intentionally browser-visible build settings. Use runtime secret files for the CMS token and auth signing key; adapt the application to read those files as part of future implementation. No new `GATSBY_` aliases are planned. The CMS URL and browser settings are not credentials; document which values are embedded at build time and require a new image when changed.

## Server and routing

Recommend Debian 13 on x86_64, with systemd and a Podman version whose Quadlet features have been verified on the selected VPS image. Ansible installs and configures system-managed Quadlets: Podman itself runs as a rootful system service manager, while Traefik, auth and Astro run as explicit non-root container processes with dropped capabilities, no privilege escalation and read-only filesystems where feasible. Rootful Podman is not rootless isolation; host root and the engine remain privileged. Set appropriate file ownership, port and network permissions, cgroup v2, SELinux/AppArmor policy and persistent writable paths deliberately. Rootless Quadlets are an alternative for later evaluation, not an implied requirement for the first deployment. [Podman Quadlet documentation](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html)

Traefik is the only service publishing host ports 80 and 443. Auth and Astro are reachable only over the private container network; restrict access to that network and the host because other local containers or host administrators could bypass the proxy. Traefik uses an explicit file provider and fixed service/router configuration, with no Podman or Docker engine socket. Do not expose an unauthenticated dashboard. Route login and logout explicitly to auth; apply forward authentication to every other preview route, including static assets and HTTP health endpoints, with failure closed. Only minimal approved identity headers should be forwarded, after stripping browser-supplied equivalents and credentials. Restrict trusted proxy headers to verified upstream addresses; configure rate limiting based on a trustworthy client address. Apply no-store/noindex and an exact configured CMS `frame-ancestors` policy to every response, including static assets, errors and login responses. Configure and verify a Cloudflare cache bypass for the entire preview hostname.

Traefik obtains and renews certificates using ACME DNS-01. Use a Cloudflare API token scoped to the needed zone with Zone Read and DNS Edit, supplied only to Traefik as a mounted secret; persist and protect ACME account/certificate state. Test against the ACME staging service before production and exercise renewal. DNS-01 is certificate verification, not user authentication. [Traefik ACME documentation](https://doc.traefik.io/traefik/v3.4/https/acme/) and [Cloudflare DNS provider permissions](https://go-acme.github.io/lego/dns/cloudflare/).

## Authentication and editor behavior

On login the auth service sends credentials to Strapi's administrator login over HTTPS, validates the returned administrator identity and required active/role status via the appropriate admin endpoint, and immediately discards the upstream administrator token **and any refresh cookies**. Do not forward either to the browser, Astro or logs. Fail closed for network failures, timeouts, invalid responses and unavailable session storage. This is one verification per login, not a persistent Strapi session or a redesign of Strapi authentication.

Issue a separate signed preview JWT in a Secure, HttpOnly cookie using an explicitly fixed allowed algorithm, issuer and audience, expiration and unique `jti`. Initial policy: **eight-hour absolute lifetime and one-hour inactivity timeout**, subject to implementation and editor testing. Maintain an active-session record keyed by `jti` in a small, private, persistent SQLite file; check it on each authenticated request and update idle state safely. Logout revokes the preview session immediately. Handle concurrent requests, expiration, restart, cleanup and signing-key rotation explicitly. A signed JWT alone cannot guarantee immediate logout without server-side state. No separate database server is needed. Preview logout does not log out of Strapi, and CMS logout or role changes do not automatically revoke an already issued preview session; an administrator whose CMS access changes can retain access until preview session expiry or explicit revocation. Document this tradeoff and provide an operator revocation procedure.

Protect login/logout against CSRF and untrusted redirect destinations, validate request size and content, rate-limit failed attempts, use bounded upstream calls, and do not log credentials, tokens, CMS bodies or draft URLs. Keep preview JWT signing material separate from Strapi Content API tokens, registry credentials and DNS tokens. Plan signing-key rotation with an explicit choice between a short verification overlap and signing out all sessions; do not restore a compromised key during rollback.

Saved drafts are fetched at request time, including new and renamed documents; there is no Gatsby refresh endpoint or rebuild for a save. Restore the CMS URL-resolution and verified saved-draft refresh integration only after Gatsby retirement, validating message origin and source. Unsaved editing is not promised. Check newly created, renamed, deleted, published and incomplete drafts and avoid generating malformed preview URLs. Cross-site cookies and identity redirects can prevent iframe login even when headers are configured. Test the actual CMS origin and editor browsers; a direct preview tab is a fallback, not evidence that iframe acceptance passed.

## How Ansible fits

Ansible is a checklist executed from the operator's laptop. Its playbooks describe the desired server state, check the server, and make only the changes needed to reach it; they do not rely on remembering which commands were run last time. An inventory identifies the target VPS, and roles group setup for packages/security, Podman/network, secrets, Traefik, auth and Astro. Verify repeat runs are safe and understandable. The future preview repository must include a beginner setup guide explaining SSH access, installation, inventory, Vault passwords, dry runs, review, deployment, updates and recovery with concrete commands.

Use Ansible Vault to encrypt secrets stored in the private repository and decrypt them locally only for the run. Vault protects data at rest, not values in use: Ansible installs scoped, owner-readable secret files on the server, tasks handling them use `no_log`, and plaintext is not echoed into CI output, world-readable environment files, images or logs. Restrict each mounted file to the one service that needs it. Record secret ownership and reload/restart behavior. Test a rotation by installing the replacement, restarting/remounting where necessary, verifying the dependency, and only then revoking the old value. [Ansible Vault documentation](https://docs.ansible.com/projects/ansible/latest/vault_guide/vault.html)

## Delivery and recovery

After WEB-46, create the preview repository and implement in reviewable increments: authentication and its tests; platform/Quadlet/Traefik provisioning; immutable preview-image packaging; CMS/editor integration; then deployment, acceptance and recovery evidence. The ticket index records the board's actual dependency links. Before any real-host rollout, review the generated configuration, exact image digests, secret boundaries, DNS and rollback procedure. A deployment pre-pulls images, validates Quadlets and Traefik, starts the required private services, checks liveness and dependency readiness, and then checks the protected route. Failure must leave or restore the last known-good compatible image/configuration set. A single-instance replacement may briefly interrupt service; use parallel instances only if a measured uptime requirement warrants their complexity.

Retain previous reviewed image digests, matching service/config versions, persistent session state and recovery instructions for the agreed retention period. Plan for DNS, certificate state and authentication-signing-key compatibility; never reinstate a compromised secret as part of rollback. Verify boot recovery, restore, token rotation, Strapi/auth outages, missing/invalid session behavior, anonymous access, cache headers and real iframe behavior on the new host. Measure startup, memory, latency and saved-draft freshness; local build results do not substitute for host evidence.
