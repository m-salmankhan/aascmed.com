# Shared content contracts

`models.ts` is the serializable boundary shared by Gatsby and Astro. Views receive plain content, blocks, site settings, and media descriptors; they do not receive `Queries.*`, Gatsby nodes, `localFile` trees, React elements, or credentials. Strapi Blocks and dynamic-zone data remains structured JSON until a React view renders it.

`gatsby-adapter.ts` is the Gatsby-side adapter. It selects only fields used by shared views, translates Gatsby's snake-case component fields to stable names, converts Gatsby image data to `MediaDescriptor`, and extracts only the requested `body` or `content` arrays from `internal.content`. Malformed or absent optional content is omitted. A REST adapter should map fields into these same models, keep Blocks/dynamic-zone values as JSON, and keep its server token outside the returned data.

`shared/data/site-data.tsx` defines the serializable site metadata used by shared React UI. Gatsby provides it through `src/adapters/gatsby/site-data.tsx`; the focused `src/adapters/gatsby/announcement.tsx` adapter separately queries announcement content and passes it directly to `AnnouncementBanner`. Gatsby page queries already supply clinic summaries to the home and contact views, which pass clinic names explicitly through `ContactSection` to `ContactForm`. SEO receives tracking settings through its own Gatsby wrapper query because the Head API runs outside the site-data tree. Astro layouts and islands can supply only the plain values their components need.

`urls.ts` holds pure detail-path rules. Blog, condition, provider, and clinic paths keep trailing slashes. Clinics use the current lowercase, whitespace-to-hyphen name fallback when no explicit slug exists. Service updates retain the `/service-updates/YYYY/MM/slug/` route; missing or invalid dates and missing slugs return `null`. Inspection corrected the earlier undated-fallback assumption: `gatsby/create-pages.js` formats `moment(node.date)`, and Moment treats a missing date as the current build date. There is no undated service-update route in the captured baseline, so published records require a valid date and drafts can wait until one exists.

`validateContentRecord(record, family, mode)` provides the publishing boundary. Draft mode accepts incomplete editorial records. Published mode requires an ID, title, and route for that content family; a clinic name can supply the fallback slug. Optional body, content, and media fields remain optional. Run it on normalized records before emitting public routes.

Adapters preserve the ordering selected by their query. Astro REST loaders should request ordering from Strapi (`order:asc` for condition/provider lists and `date:desc` for blog/update lists), add a deterministic secondary key for stable pagination, fetch every page before applying display limits, and compare tie ordering with the Gatsby baseline. The local `sortByOrder` and `sortByDateDescending` helpers are for fully materialized in-memory arrays only; do not sort individual pages after pagination. Strapi REST supports sorting and pagination through its [REST API parameters](https://docs.strapi.io/cms/api/rest/). Keep homepage retired-provider filtering at the consuming query/view boundary. Contract fixtures are in [`tests/unit/content-contracts.test.mjs`](../../../tests/unit/content-contracts.test.mjs); the captured route reference remains [`tests/ui/routes.json`](../../../tests/ui/routes.json).
